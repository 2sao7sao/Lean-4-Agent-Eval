# 贯穿案例：原始数据到统计报告／PPT

这是教学用假设案例，所有口径和数值均为示例，不是用户已经批准的生产标准。

## 用户看到的沟通

用户：“把这份销售数据整理成季度经营汇报，让负责人知道收入变化和主要问题。”

系统先阅读字段，提炼可确认的事实，再补三个高价值问题：

1. 这次以哪个字段和期间为准？退款、税、币种如何处理？
2. 负责人需要据此做什么决定？哪些信息必须包含？
3. 有无参考报告、时间／成本上限，以及不能执行的动作？

系统回显：已确定的口径、默认建议、仍未确定的地方、成功与失败例子。对话产出合同草稿，再开始探索运行。只有在关键口径与验收规则明确后，才能用它作正式验收依据。

## 合同的一个具体切片

最初实验只关心已清洗的三条整数金额：`10000, 20000, -2000` 分，净额应为 280 元。假设币种相同、时间范围已选好、退款为负数。这些是教学输入约定，不代表清洗与业务口径已经被证明。

| ID | 要求 | 证据与方法 | 验收类型 |
|---|---|---|---|
| T1 | 使用指定输入版本 | 独立采集的读取记录与快照标识 | trace 硬检查 |
| T2 | 计算记录与输入一致 | 重算金额；核对计算事件的输入与输出 | trace 硬检查 |
| T3 | 导出使用了对应计算产物 | 计算事件 → 导出事件的因果连接 | trace 硬检查 |
| O1 | 报告净额为 280 元 | 从最终文件提取可见值并重算比对 | 端到端硬检查 |
| O2 | 文件能打开，页面元素可见 | 实际渲染，检测溢出、遮挡、空白页 | 端到端检查＋视觉复核 |
| O3 | 重要结论有可定位的依据 | 结论到表／图／来源映射与支持度判断 | 程序＋经校准模型／人工 |
| O4 | 汇报能回答负责人关心的问题 | 受众任务与锚点样例评分 | 经校准模型／人工 |

T1–T3 即使全部通过，也推不出 O1–O4。O1 正确也推不出 T1–T3 正确。只有规约覆盖完整、状态连接成立时，局部正确性才能用于推导整体属性。

`labs/01_contract_lab.py` 将 T1–T3 合并为两个狭窄 trace 检查，并模拟 O1。它不解析或生成真实 PPT，也未实现 O2–O4。

## 端到端样本要覆盖什么

先做一小组人工可审查的开发样本，例如正确输入、退款、重复行、缺失值、零分母、多币种、跨期记录、不可读文件、图表轴误导、结论超出数据、正确计算但错误展示。具体数量由覆盖目标和预算决定；这组开发样本不能直接支持可靠性的总体结论。

对不同任务分支复用基础设施，而不是把同一份评分表套到所有任务：

- 编程：增加干净环境运行、隐藏功能用例、既有功能回归和可维护性检查。
- 数据挖掘：增加数据划分、泄漏检查、基线比较、不确定性和因果措辞检查。
- PPT：增加真实文件解析、渲染、图表和页面上的值核对、阅读顺序检查。
- 文案：增加来源支持、必要信息覆盖、受众和文风校准。

## 自动生成评估时，先验证生成的评估器

从一份已知正确的产物出发，定向引入缺陷：把 280 改成 300、替换来源、删除关键页、改变单位、伪造引用、删除 trace 片段。检查预期规则是否拦截，避免只测试“正确答案会通过”。

再做不该改变结论的变化：金额行重排、同一计算拆组、等价表达、合理布局变化。检查是否误拒绝。如果规则强制某一种工具顺序，可能拒绝同样正确的替代方案。

这些变异／关系测试验证的是评估器行为。它们不是生产成功率，也不替代 Lean 的全称证明。

## 下一次共建时需要的最小输入

选择一个具体办公任务，用一小份可分享或合成的数据，给出一个满意结果的例子和一个不能接受的错误。我们先一起确定三至五条真正影响验收的规则，再安装和固定 Lean 工具链、证明其中最清晰的一条。

不需要一开始提供整个业务系统，也不需要先掌握复杂数学。最初要学会的是：把“结果不错”拆成可观察、可检查、可解释的要求。
