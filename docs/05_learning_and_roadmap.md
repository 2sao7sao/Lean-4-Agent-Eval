# 一起学习与构建的路线

已知起点：用户从零学习 Lean；目标应用是办公 agent。下面按产出推进，不以看完教材或固定日程代表掌握。

## 每轮怎么合作

一轮只集中解决一个问题：我用当前任务解释概念 → 我们共同修改一条规则或一个例子 → 运行／检查 → 解释它支持什么、还缺什么 → 将结论写进项目文档。

用户负责判断业务目标、满意与不满意的实例、实际取舍；助手负责资料定位、精确化草稿、实现、检查与证据记录。对理解程度只根据实际讨论和修改判断，缺少作答不解释为不会。

## 阶段与交付

| 阶段 | 学习重点 | 共同产出 | 进入下一阶段的证据 |
|---|---|---|---|
| 0 原理 | 命题、证明、测试、统计区别 | 第一课、数据小实验 | 能用一个例子说清“证明覆盖什么” |
| 1 任务定义 | 需求变成可检查规约 | 一个真实任务的合同和正反例 | 关键口径明确，规则有证据入口 |
| 2 Lean 小例子 | 类型、命题、简单证明、归纳 | 合计检查器／聚合规则之一 | 固定工具链，编译和公理审计留下记录 |
| 3 过程与结果 | trace、最终产物、证据缺口 | 单个 agent 的运行器和检查器 | 已知缺陷被发现，等价方案不误拒绝 |
| 4 可靠测量 | 校准、区间、抽样和重复运行 | 人工样本、评分校准、实验协议 | 误差可见，分母明确，结论范围正确 |
| 5 自动迭代 | 对照、回归、冻结验收 | 有预算上限的改进循环 | 改进不靠改评分规则或泄漏验收集 |
| 6 多办公任务 | 共享合同与专用适配器 | 编程／统计／分析／PPT／文案扩展 | 每个新增任务类型独立通过适配验收 |

这些是路线和验收建议，不是已发生的学习或测试结果。

建议第一条讨论题：当计算正确、PPT 数字正确，但“广告导致增长”的结论缺乏因果证据时，我们应该让哪些规则通过、哪些规则失败或保留不确定？

这个问题能同时练习规格、证据与判断边界，不需要先掌握 Lean 语法。

## 哪些设计还没有答案

首个实际 agent 的运行入口、数据源、产物格式、允许的外部动作、费用预算、质量与时效取舍尚未确定。它们不阻碍原理学习和离线实验，但决定真实接入与正式验收方式。

2026-11-15 工程进展：已完成首批形式化规则与可重复检查脚本；尚未取得用户独立练习或业务验收结果，不能据此更新为“已掌握 Lean”或“办公 agent 已验证”。

架构中也有待研究的问题：形式化子集的表达能力、自然语言到规约的误差如何测量、trace 完整性如何由运行环境保障、PPT 和分析质量如何形成可重复的人类标准。后续应以小实验逐项解决。
