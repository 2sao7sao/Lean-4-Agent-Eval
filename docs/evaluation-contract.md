# 评估合同与结论语义

合同是验收约定。每条要求追溯到用户原话或明确标记的假设，每条检查指向要求和证据。当前 Schema 是 v0.1 草案，尚未定义所有生产运行对象。

## 字段与冻结条件

| 字段 | 用途 |
|---|---|
| `schema_version / contract_id / version` | 结构与业务版本 |
| `status / approved_by / open_questions` | 草案、冻结状态及澄清条件；生产中还须验证确认真实性 |
| `goal / source_request / assumptions` | 目标、需求来源及待审查假设 |
| `inputs / deliverables` | 输入约束、交付格式与路径 |
| `requirements` | 唯一 ID、来源、验收描述及是否必检 |
| `evidence_requirements` | 种类、生产者、采集完整性要求 |
| `checks` | 绑定要求、证据、检查器版本、实现状态、方法与参数 |
| `decision_policy` | 必检聚合语义 |
| `experiment_plan` | 任务分层、集合隔离、重复与预算原则 |
| `intake`（生成合同） | 编译器版本、显式字段及来源、需求确认和审查哈希 |

结构见 [contract.schema.json](../schemas/contract.schema.json)，实例见 [样例合同](../examples/sales-to-ppt/contract.json)。

静态校验拒绝空必检集、重复 ID、未知引用、没有必检覆盖的强制要求，以及带未决问题或待实现检查器的冻结合同。通过只表示这些条件满足，不能推断需求充分、检查器正确或真实批准。

M1 增加字段来源覆盖与审查确认一致性检查。手工基准样例可不含 `intake`；编译器输出必带该字段。生成合同确认只确认需求和提议标准，`approved_by` 保持为空，状态保持 draft。执行冻结还需要业务验收器、确认身份与运行条件就绪。

审查哈希覆盖合同全部内容，仅排除 `intake.requirements_confirmation` 自身。它是内容一致性检查，不是身份认证；不能抵抗同时篡改合同与重算哈希。详细状态和接口见 [M1 使用说明](intake.md)。

## 检查方法

- `deterministic`：解析、独立计算、精确相等或明确容差。
- `runtime_policy`：基于可信执行边界检查权限、顺序和副作用。
- `model_judge`：版本化量表；需标注校准集、误差统计、分歧处理。
- `human_review`：保存复核人、量表、所看证据和结论。
- `formal`：仅在提供可检查证明、已验证命题和明确前提时使用。

必检质量分数通过固定阈值转换为判定，原始分数与校准状态另存。未经校准的质量裁判不能成为已满足的发布条件。

## 四种判定

| 判定 | 含义 | 例子 |
|---|---|---|
| `PASS` | 当前检查在声明证据和范围内满足标准 | 净销售额与独立计算一致 |
| `FAIL` | 有证据显示违反标准 | PPT 金额错误；未授权外发 |
| `UNKNOWN` | 证据不足 | 所需工具事件不可见 |
| `ERROR` | 评估或采集机制故障 | 渲染器不可用、检查器崩溃 |

产物本身损坏且能确认是提交内容，属于交付失败；检查器无法运行属于评估故障。任务完成且收集完整时未提交必需文件属于失败，不能确定是否收集则属于未知。

## 必检聚合

必检清单由合同决定，Agent 或回执列表不能自行缩小。

1. 任一必检 `FAIL` → `FAIL`。
2. 无失败但存在 `ERROR` → `ERROR`。
3. 无失败/错误但存在 `UNKNOWN` 或缺失必检回执 → `UNKNOWN`。
4. 必检集合非空且全部 `PASS` → `PASS`。
5. 空合同 → `UNKNOWN`，同时静态校验应拒绝它。

附加诊断项不参与业务通过聚合，但始终保留。硬约束不可被平均分抵消。禁止复用不同运行、合同哈希或检查器版本的回执；重复/冲突回执属于边界错误，不能任取一项。

[回执 Schema](../schemas/receipt.schema.json) 只校验形状；运行绑定、哈希匹配、证据可信性和证明有效性由执行层另行校验。当前没有可接受任意回执并宣称业务通过的运行接口。
