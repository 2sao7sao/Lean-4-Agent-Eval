# 第一课：Lean 究竟验证什么

## 从一张销售表开始

假设约定：金额用“分”表示，正数是收入，负数是退款。三条记录是 `10000, 20000, -2000`，合计为 `28000` 分。

Agent 写出：“净收入 280 元，并已制作汇报。”至少有五个不同的问题：

1. 加法有没有算错？
2. 用的是指定文件和正确版本吗？
3. “净收入”的口径是否该减去退款，时间范围是否正确？
4. PPT 上真正显示的是 280，还是生成过程中变成了 300？
5. 根据这几个数写出的业务建议有依据吗？

这五个问题需要不同证据。一个加法证明不能自动回答后四个问题。

## Lean 的工作机制

Lean 是编程语言和交互式定理证明工具。形式化验证先把对象、规则和目标写成精确的形式，再建立目标成立的证明。它以依赖类型理论为基础。[官方引言](https://lean-lang.org/theorem_proving_in_lean4/Introduction/)、[类型理论](https://lean-lang.org/theorem_proving_in_lean4/Dependent-Type-Theory/)

初学时先理解这些概念：

| 概念 | 在本项目里的例子 |
|---|---|
| 定义 definition | 明确定义“合计”是对整数金额列表求和 |
| 命题 proposition | “如果合计检查器接受，申报合计等于列表合计” |
| 假设 assumption | 输入列表按约定口径形成、整数单位为分 |
| 证明 proof | 依据定义和规则，建立命题成立的对象 |
| 核验 checking | 检查该证明是否确实证明了这个命题 |

“命题即类型、证明即项”可以先理解为：每个命题规定一种合格证据的形状，证明必须满足这种形状。证明 `A ∧ B` 要给出 A 和 B 各自的证明；证明 `A → B` 要给出从 A 的证明得到 B 的证明的方法。[Propositions and Proofs](https://lean-lang.org/theorem_proving_in_lean4/Propositions-and-Proofs/)

Tactic 是构造证明的指令。人、自动化程序或 LLM 都可以尝试构造证明；Lean 将表层表达展开为核心形式，由内核检查。这个分工使复杂的“找答案过程”和较小的“检查答案机制”能够分离。[Tactics](https://lean-lang.org/theorem_proving_in_lean4/Tactics/)、[Elaboration and Compilation](https://lean-lang.org/doc/reference/latest/Elaboration-and-Compilation/)

```mermaid
flowchart LR
    A[人想表达的要求] --> B[精确定义和命题]
    B --> C[人或 AI 构造证明]
    C --> D[Lean 内核检查]
    D --> E[该命题在声明前提下成立]
    A -. 需要语义核对 .-> B
```

最容易漏掉的是第一条边：“人想要的要求”是否被准确翻译成“精确命题”。Lean 核验的是后者。

## 测试与证明的差别

测试可以检查列表 `[10000, 20000, -2000]` 得到 28000。更强的测试会覆盖空列表、负数、重排、很多随机列表。

形式化证明可以针对**全部符合定义的整数列表**证明某个关系，例如：分成两组分别求和再相加，等于直接对拼接后的列表求和。这是一个关于定义的全称命题，不是“抽样很多次没有出错”。

但这不意味着所有现实问题都能自动证明。数学整数不等于任何语言里的固定宽度整数或浮点数；还需要处理解析、溢出、舍入、缺失值以及程序和形式模型之间的对应关系。

## 能迁移到 Agent 评估的核心思想

最有价值的是：**先说明承诺，再要求可核验的证据，最后让明确的检查规则作判断。**

例如 agent 提交结果时，同时提交：使用的数据版本、口径、计算产物、关键结论与来源映射。独立评估器重新计算，核对最终产物，再根据规则给出结论。

这些材料通常只是“证据包”，不是 Lean 意义上的证明项。只有形式化命题、证明以及通过检查的对应记录齐全时，才把那一部分称为形式化证明。

可以考虑在 Lean 中验证：

- 一个合计检查函数的接受条件与精确规范等价。
- 既定状态机中的某类动作必须发生在有效授权之后。
- 验收聚合逻辑不会在必检项缺证据时返回通过。
- 分组计算规则保持某种业务不变量，前提是业务语义已形式化。

不能因此自动推出：

- 上游数据库记录真实且没有漏报。
- 需求理解完全正确、用户选择了正确业务口径。
- 模型关于市场、原因、建议的自然语言判断都正确。
- 没有日志的动作没有发生。
- 有限测试证明 agent 在未知任务上永远成功。

## 如何避免“证明了一个没用的东西”

例一：把 `业务结论正确` 直接当作公理，再推出报告正确。这只是把待验证的结论放进前提。

例二：声明“在金额既大于 100 又小于 0 的条件下，检查器正确”。前提不可能成立，无法帮助实际验收。

例三：只证明 `输出 = 输出`，却把定理命名为“报告准确”。名字不能扩大定理的含义。

因此需要检查定理内容、前提是否可满足、是否覆盖真实需求，以及公理依赖。`sorry`／`admit` 表示未完成证明；不能只看构建成功。`#print axioms` 可以检查传递公理依赖，`native_decide` 会扩大所信任的实现范围。对自动生成的证明，还需考虑在隔离环境中重新核验、固定工具链和依赖。[Validating a Lean Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)、[Tactic Reference](https://lean-lang.org/doc/reference/latest/Tactic-Proofs/Tactic-Reference/)

## 本课的小实验

运行 `python3 labs/01_contract_lab.py`，关注两种情况：

- 过程证据显示计算得到 280，最终材料却写 300。
- 最终材料写了 280，但没有任何过程记录。

第一种情况可以在结果验收中判失败；第二种情况可以确认狭窄的数值正确性，但不能确认使用了指定来源或遵循了过程要求。

本课可讨论的问题：如果 PPT 写着“净收入增长，因此广告投放有效”，我们能从合计正确推出什么？还缺少哪些证据？不要求现在答题；后续以你的实际判断和修改为学习依据。
